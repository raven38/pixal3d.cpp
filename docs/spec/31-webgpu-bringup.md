## 2. Backend layout & build

### Directory layout (identical in both `ggml-org/ggml` and `ggml-org/llama.cpp`'s `ggml/`)

```
include/ggml-webgpu.h                       # 19-line public header: ggml_backend_webgpu_init(), ggml_backend_webgpu_reg()
src/ggml-webgpu/
  ggml-webgpu.cpp                           # 4790 lines: entire backend (device mgmt, encode, dispatch, supports_op)
  ggml-webgpu-shader-lib.hpp                # shader-variant selection helpers (tile/subgroup-matrix decision logic)
  pre_wgsl.hpp                              # WGSL preprocessing helpers used by embed_wgsl.py at build time
  CMakeLists.txt                            # shader embedding + Emscripten/Dawn wiring (below)
  wgsl-shaders/
    embed_wgsl.py                           # Python: globs *.wgsl + *.tmpl -> generates ggml-wgsl-shaders.hpp at build time
    *.wgsl (54 files)                       # one shader family per op group (mul_mat*, flash_attn*, binary, unary, glu, norm, conv2d*, rope, soft_max, argsort, cumsum, ssm_*, gated_delta_net, solve_tri, ...)
    *.tmpl (7 files)                        # shared WGSL text templates (mul_mat_decls, flash_attn_decls/staging, common_decls, quant_inner_loops, mul_mat_vec_*_acc)
```

There is **no ahead-of-time shader compilation step** to a binary format —
`.wgsl`/`.tmpl` source text is embedded as C++ string literals
(`ggml-wgsl-shaders.hpp`, generated by `embed_wgsl.py` at CMake-configure/build
time) and compiled by Dawn/the browser's WebGPU implementation at
`ggml_webgpu_create_pipeline()` call time (JIT, first-use per op+dtype
variant).

### CMake options (root `CMakeLists.txt`, both repos, identical apart from a
one-line offset caused by unrelated additions upstream)

```
option(GGML_WEBGPU                          "ggml: use WebGPU"                                OFF)
option(GGML_WEBGPU_DEBUG                    "ggml: enable WebGPU debug output"                OFF)
option(GGML_WEBGPU_CPU_PROFILE              "ggml: enable WebGPU profiling (CPU)"             OFF)
option(GGML_WEBGPU_GPU_PROFILE              "ggml: enable WebGPU profiling (GPU)"             OFF)
option(GGML_WEBGPU_JSPI                     "ggml: use JSPI for WebGPU"                       ON)
```

`GGML_WEBGPU_DEBUG` adds `-DGGML_WEBGPU_DEBUG=1` and, under Emscripten, links
`-sASSERTIONS=2`. `GGML_WEBGPU_CPU_PROFILE` / `GGML_WEBGPU_GPU_PROFILE` each
just define a macro consumed by `WEBGPU_CPU_PROFILE_TOTAL_START/END` timing
macros in `ggml-webgpu.cpp`; GPU profiling additionally requests the
`TimestampQuery` WebGPU feature at device-creation time. `GGML_WEBGPU_JSPI`
picks Emscripten's exception/suspend strategy (below). `EMDAWNWEBGPU_DIR` is a
plain `CACHE PATH`, no default value, read only under `EMSCRIPTEN`.

### Native path (`src/ggml-webgpu/CMakeLists.txt`, non-Emscripten branch)

```cmake
find_package(Dawn REQUIRED)
set(DawnWebGPU_TARGET dawn::webgpu_dawn)
...
target_link_libraries(ggml-webgpu PRIVATE ${DawnWebGPU_TARGET})
```

No version/commit pin is asserted in CMake itself (no `find_package(Dawn
1.2.3)`); the Dawn commit compatibility guarantee (`18eb229`) is documentation-only,
in `docs/build.md`. `find_package` requires the user to have built/installed
Dawn locally and exposed it via `CMAKE_PREFIX_PATH` — there is no
`FetchContent`/vendoring of Dawn in either repo.

### Emscripten / browser path

```cmake
if(EMSCRIPTEN)
  set(EMDAWNWEBGPU_DIR "" CACHE PATH "Path to emdawnwebgpu_pkg")
  if(NOT EMDAWNWEBGPU_DIR)
    target_compile_options(ggml-webgpu PRIVATE "--use-port=emdawnwebgpu")       # built-in emscripten port
    target_link_options(ggml-webgpu INTERFACE "--use-port=emdawnwebgpu")
  else()
    target_compile_options(ggml-webgpu PRIVATE "--use-port=${EMDAWNWEBGPU_DIR}/emdawnwebgpu.port.py")
    target_link_options(ggml-webgpu INTERFACE "--use-port=${EMDAWNWEBGPU_DIR}/emdawnwebgpu.port.py")
  endif()
  if (GGML_WEBGPU_JSPI)
    target_compile_options(ggml-webgpu PRIVATE "-fwasm-exceptions")
    target_link_options(ggml-webgpu INTERFACE "-sJSPI" "-fwasm-exceptions")
  else()
    target_compile_options(ggml-webgpu PRIVATE "-fexceptions")
    target_link_options(ggml-webgpu INTERFACE "-sASYNCIFY" "-exceptions")
  endif()
endif()
```

So: emdawnwebgpu (Dawn's own Emscripten WebGPU bindings, since Emscripten has
no official WebGPU bindings) is consumed as an Emscripten **port**
(`--use-port=emdawnwebgpu`, resolved from Emscripten's own port registry
unless `EMDAWNWEBGPU_DIR` points at a locally built package — recommended by
`docs/build.md` "so that it stays in sync with the version of Dawn you have
installed" natively). There is a hard fork between `JSPI` (`-sJSPI
-fwasm-exceptions`, default ON) and `ASYNCIFY` (`-sASYNCIFY -exceptions`,
opt-in via `-DGGML_WEBGPU_JSPI=OFF`) for how the backend suspends the wasm
call stack across async `RequestAdapter`/`RequestDevice`/buffer-map
callbacks — this is a real fork in the browser build's runtime requirements:
JSPI needs a browser with the JS Promise Integration proposal (Chrome
≥123 behind flag / ≥130 stable-ish as of the ggml pin era); ASYNCIFY works
everywhere WebAssembly does but bloats binary size and adds call overhead.
Neither pthreads nor memory64 flags appear anywhere in this CMakeLists or in
`ggml-webgpu.cpp`/`ggml-webgpu-shader-lib.hpp` — the WebGPU backend itself has
no compile-time pthreads/memory64 requirement (any such requirement would come
from ggml-cpu / the rest of the wasm module, not this backend).

## 3. Backend API vs the trellis fork's v0.15.1 core

**Central finding — the planning docs are wrong on their most load-bearing
claim.** `CLAUDE.md` states *"`GGML_WEBGPU` doesn't exist yet on this fork's
vendored `thirdparty/ggml` ... WebGPU is future work."* This is false as of
the pinned commit actually checked out in this repo
(`thirdparty/ggml` @ `737e88f2`, verified `git rev-parse HEAD` == the
submodule's recorded pin, working tree clean, no local patches):

```
$ ls thirdparty/ggml/src/ggml-webgpu/
CMakeLists.txt  ggml-webgpu-shader-lib.hpp  ggml-webgpu.cpp  pre_wgsl.hpp  wgsl-shaders/
$ grep -n webgpu thirdparty/ggml/CMakeLists.txt
option(GGML_WEBGPU ...) option(GGML_WEBGPU_DEBUG ...) ... (all 5 options present)
$ grep -n WebGPU thirdparty/ggml/src/CMakeLists.txt
ggml_add_backend(WebGPU)     # ordinary, unconditional entry, same macro as CUDA/Vulkan/Metal
```

`ggml-webgpu.cpp` in the fork is 4583 lines, already implements
`ggml_backend_webgpu_init`, `ggml_backend_webgpu_reg`,
`GGML_BACKEND_DL_IMPL(ggml_backend_webgpu_reg)`, subgroup-matrix and tiled
FlashAttention paths, `TOP_K`, `GATED_DELTA_NET`, `ADD_ID`, `XIELU`, etc. — a
mature backend, not a stub. `PIXAL3D_OP_SUPPORT_MATRIX.md`'s framing
("Revalidate only the WebGPU operator coverage ... because backend support
changes over time") is directionally right but understates how far along the
starting point already is.

### Backend-interface diff: fork's `ggml-backend-impl.h`/`ggml-backend.h` vs upstream tip

`GGML_BACKEND_API_VERSION` is **2 in both** — unchanged across the v0.15.1 →
v0.23.0 gap. `diff` of the two `ggml-backend-impl.h` files shows exactly two
additions on top, neither of which the WebGPU backend actually exercises:

1. `ggml_backend_i::graph_optimize` gained a third parameter
   (`struct ggml_backend_graph_optimize_params * params`, carrying an
   `add_alloc_dep` callback for backends that execute out of order on
   concurrent streams). **Irrelevant here** — `ggml-webgpu.cpp`'s
   `ggml_backend_webgpu_i` sets `/* .graph_optimize = */ NULL`; it never
   defines this hook in either version.
2. `ggml_backend_dev_caps` gained one new field, `bool mmap_support`, appended
   after `events`. **This one bites**: current `ggml_backend_webgpu_device_get_props()`
   initializes the struct positionally with 5 members including
   `/* .mmap_support = */ true`, one more than the fork's 4-member
   `ggml_backend_dev_caps`. Dropping straight into the fork's core as-is would
   fail to compile (`ggml-webgpu.cpp:3972`, too many initializers). Also new,
   unused by this backend: free function `ggml_op_alloc_size_may_expand()`
   and `ggml_backend_meta_buffer_set_usage()`.

`ggml-backend.h` (public) diff: identical except `struct ggml_backend_dev_caps`
gains the same `mmap_support` field — same root cause, same fix needed
(either add the field to the fork's `ggml_backend_dev_caps`, which is
source-/ABI-additive and safe since it's a plain trailing bool, or drop that
one initializer line when syncing `ggml-webgpu.cpp` into the fork).

### Actual content diff between the fork's `ggml-webgpu.cpp` (pinned, effectively pre-June-2026 vintage per its own last touching commits) and upstream tip (Sept 2026)

`diff -u` : 906 diff lines total (151 removed / 358 added) out of 4583→4790
source lines — an incremental few-months' drift, not a rewrite. The only
**operator-support-table** changes in that diff are additive:

- `GGML_OP_CONV_2D_DW` support added upstream (fork has no case for it —
  falls to CPU today). New shader `conv2d_dw.wgsl` shipped upstream; absent
  from the fork's `wgsl-shaders/`.
- `GGML_GLU_OP_SWIGLU_CLAMP` added to the `GGML_OP_GLU` switch upstream.
- Flash-attention quantized-KV staging was refactored from one template
  (`flash_attn_quant_staging.tmpl`, in the fork) into two
  (`flash_attn_decls.tmpl` + `flash_attn_staging.tmpl`, upstream) — a
  reorganization, not a behavior change for the F32/F16 K/V paths Pixal3D
  needs.
- The rest of the diff is perf tuning (subgroup-matrix tile-size heuristics),
  the offset%4 `ggml_backend_tensor_get` crash fix, `ggml_rope_set_offset`
  plumbing for several backends, and the `mmap_support`/caps line above.

Everything else the backend needs from the core (`ggml_backend_i`,
`ggml_backend_device_i`, `ggml_backend_buffer_type_i`,
`ggml_backend_buffer_i`, `ggml_backend_reg_i`, `GGML_BACKEND_DL_IMPL`) is
**byte-identical in field layout and semantics** between the fork's pinned
`ggml-backend-impl.h`/`ggml-backend.h` and current upstream.

### Recommendation

**Do not "port" this backend from scratch, and do not do a full core rebase
onto v0.23.0 either.** The evidence:

- The backend the porting plan describes as future work is already vendored,
  wired into the build system identically to every other backend, and only
  ~3 months (906 diff lines, 2 op-support additions) behind current upstream.
- The one real core-API gap (`ggml_backend_dev_caps::mmap_support`) is a
  single trailing `bool` field — safe to add to the fork's
  `ggml-backend.h`/`ggml-backend-impl.h` without touching any other backend's
  code (it's aggregate-initialized elsewhere with named/positional
  initializers that don't overflow when a field is appended at the end; every
  other `get_props` implementation in the fork would need the same one-line
  addition or to rely on value-initialization of the new field — verify at
  patch time, not assumed here).
- Concretely: (a) cherry-pick/hand-apply the ~906-line
  `ggml-webgpu.cpp`/`wgsl-shaders/` diff (or just take upstream's file
  wholesale — it only depends on core APIs already present, `mmap_support`
  excepted) into `thirdparty/ggml`, (b) add the `mmap_support` field to
  `ggml_backend_dev_caps` in both headers, (c) set `-DGGML_WEBGPU=ON` with a
  locally built Dawn (`18eb229`-compatible) and confirm native bring-up
  before touching Emscripten. This is materially less work and risk than
  either "port the backend into the fork" (it's already there) or "rebase the
  fork's CUDA/Vulkan patch set onto v0.23.0" (that would drag in 8 minor
  versions of unrelated core churn to fix one struct field).
- Phase ordering per `PIXAL3D.md` ("9. Integrate/enable GGML WebGPU" before
  "10. Port only unsupported Pixal3D operations to WGSL") is still correct
  and now cheaper than planned: step 9 is "sync ~900 lines + add one struct
  field + install Dawn", not "vendor a new backend."

## 5. Limits and memory behavior

- **Adapter/device negotiation**: `ggml_backend_webgpu_request_adapter()`
  calls `instance.RequestAdapter()` with an otherwise-default
  `RequestAdapterOptions` (no `powerPreference`/`forceFallbackAdapter`
  override); native-only, it enables Dawn toggles
  `vulkan_enable_f16_on_nvidia` and `use_vulkan_memory_model` on the adapter
  request (comment cites `https://issues.chromium.org/issues/42251215` as a
  tracked-toggle TODO). It then reads back `adapter.GetLimits()` and
  **requests exactly those limits back from the device** (`dev_desc.requiredLimits
  = &capabilities.limits`) — i.e. it does not request a small
  spec-minimum limit set, it asks for everything the adapter already
  reports, so device creation should not itself fail on limits (mirrors
  what the adapter offers).
- **Required WebGPU features**: `ShaderF16` always; `ImplicitDeviceSynchronization`
  and (if the adapter reports `ChromiumExperimentalSubgroupMatrix` with a
  valid F16×F16 config) `ChromiumExperimentalSubgroupMatrix`, both
  **native-only** (`#ifndef __EMSCRIPTEN__`); `Subgroups` if the adapter has
  it (native or browser); `TimestampQuery` only under
  `GGML_WEBGPU_GPU_PROFILE`. **`ShaderF16` is a hard requirement — an adapter
  without shader-f16 support cannot back this device at all.** This matters
  for browser bring-up: `shader-f16` is an optional WebGPU feature browsers
  may not expose on all GPUs/drivers.
- **Native-only Dawn perf toggles** at device creation: `disable_robustness`,
  `disable_workgroup_init`, `disable_polyfills_on_integer_div_and_mod`
  enabled, `timestamp_quantization` disabled — explicitly to "increase native
  performance" (source comment); these do not apply in the Emscripten build.
- **Buffer/binding size limits enforced by the backend itself** (not just
  passed through from Dawn): every buffer type's `get_max_size()` returns
  `capabilities.limits.maxStorageBufferBindingSize` (comment: *"maxBufferSize
  might be larger, but you can't bind more than maxStorageBufferBindingSize to
  a single binding"*) — this is the effective per-tensor ceiling, and
  `supports_op` rejects any op whose `dst`/`src0`/`src1`/`src2` exceeds it
  (checked twice: once before the op-specific switch, once after). Storage
  buffer allocations must be a multiple of 4 bytes
  (`WEBGPU_STORAGE_BUF_BINDING_MULT = 4`); `get_alloc_size()` rounds up to
  that multiple and additionally pads `ARGSORT` (`res*2 +
  minStorageBufferOffsetAlignment`, rounded) and `TOP_K` (`sizeof(int32_t) *
  nelements(src0) * 2 + alignment`, rounded) for their scratch/staging
  buffers — these two ops need materially more backing memory than
  `ggml_nbytes(dst)` alone.
- **Memory reporting is a stub**: `ggml_backend_webgpu_device_get_memory()`
  returns `capabilities.limits.maxBufferSize` for *both* `free` and `total`
  (source comment: *"TODO: for now, return maxBufferSize as both free and
  total memory"*) — there is no real free/used VRAM query; anything reading
  `ggml_backend_dev_memory()` for capacity planning on this backend is
  reading a static ceiling, not live usage.
- **Command batching**: `WEBGPU_DEFAULT_COMMAND_SUBMIT_BATCH_SIZE = 64`
  (encoded ops per submitted command buffer, tunable via
  `ggml_backend_webgpu_get_command_submit_batch_size()` which reads an env
  var override — see source around `create_webgpu_device`) and an
  in-flight-batch cap (`max_inflight_batches`), both affecting
  latency/throughput but not correctness.
- **No `cpy_tensor` buffer hook** (`/* .cpy_tensor = */ NULL` in the buffer
  interface) and no `init_tensor`/`reset` hooks — cross-backend tensor copies
  fall back to the generic `get_tensor`/`set_tensor` staging path rather than
  a device-to-device fast path.

## 6. Maturity / risks

- **Very actively developed**: 106 of the last 200 commits touching either
  repo's history (i.e. essentially the entire depth-200 shallow-clone window)
  touch `src/ggml-webgpu/` or `include/ggml-webgpu.h`. The most recent 5 in
  that window (all within roughly the last few weeks of the Sept 2026 pin):
  an offset%4 tensor-get crash fix, `SWIGLU_CLAMP` support, an
  ARGSORT/TOP_K infinity-handling fix, a WGSL include-order fix
  ("V may be defined as K in flash_attn_decls.tmpl if KV_OVERLAP" — i.e. a
  real correctness bug was live in flash-attention shader codegen until
  fixed), and `ggml_rope_set_offset` support added across
  OpenCL/SYCL/WebGPU/Hexagon. Read: this is a backend still finding and
  fixing genuine correctness bugs in its hottest paths (flash attention,
  argsort), not a settled/frozen implementation — expect to hit more such
  bugs, especially in FlashAttention's subgroup-matrix/tile path selection
  logic, which is dense and platform-conditional (§4).
- **Open TODOs found in-source** (9 `TODO`/`FIXME`/`HACK` comments total):
  CPU-profiling time handling needs rework (links to a specific llama.cpp
  PR); "TODO: error handling" on an unspecified path; buffer `init_tensor`/
  `cpy_tensor`/`reset` all explicitly marked "TODO: optional, needed?" /
  "TODO: optional, implement this" (i.e. buffer-level optimizations are
  intentionally deferred, not forgotten); the free/total memory stub (§5);
  two Dawn-toggle TODOs asking whether specific Chromium toggles are still
  needed at all (`vulkan_enable_f16_on_nvidia`, `use_vulkan_memory_model`,
  linking a live Chromium issue) — i.e. even the toggle set for correct
  native operation is not considered finalized upstream.
- **No BF16 support anywhere in the file** (confirmed by exhaustive grep) —
  if any part of the Pixal3D graph (e.g. FlashAttention BF16 K/V, called out
  in `CLAUDE.md` as "mandatory for range" on the CUDA path — "HR activations
  exceed F16 ±65504") is load-bearing on WebGPU, it will need either an F32
  fallback path or new WGSL kernels; there is currently no upstream WGSL BF16
  story to inherit.
- **No documented tested-platform matrix** in either repo (no
  `docs/backend/WEBGPU.md`, no browser/driver compatibility table found) —
  the only platform-conditional code observed is native-vs-Emscripten
  (`#ifndef __EMSCRIPTEN__`) branches for experimental/Chromium-only features
  (subgroup matrix, implicit device sync, adapter/device toggles); nothing in
  source names specific tested browsers, OSes, or GPU vendors. CI (`ci/run.sh`
  in the `ggml-org/ggml` mirror) has a `GG_BUILD_WEBGPU` env-gated native
  build/test lane but no visible browser/Emscripten CI lane in the files
  pulled for this audit.
- **Version-skew risk if left unsynced**: the fork's pinned copy is already
  ~3 months stale relative to the Sept 2026 tip (§3) and this backend changes
  every few days; whatever sync cadence the project picks for
  `thirdparty/ggml` generally will need to special-case
  `src/ggml-webgpu/` more frequently once WebGPU bring-up is live, or accept
  landing on a slightly-behind snapshot deliberately (consistent with
  `PIXAL3D_UPSTREAM_POLICY.md`'s "pin exact upstream/ggml SHAs ... don't
  update ggml and Pixal3D graph logic in the same commit" — just note WebGPU
  fixes churn faster than the rest of ggml core).
