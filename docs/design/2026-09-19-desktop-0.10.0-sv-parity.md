## 0. 「機能同等」の定義（先に固定する）

**API/機能の同等であって、出力の同等ではない。** Web と Desktop は別のバックエンド
（WebGPU/WASM と Metal/CUDA/Vulkan）で、モデルセットも別（Web=SV q8_0、Desktop=MV f16 + SV q8_0）。
同一入力・同一 seed でもバイト一致は主張しない（このプロジェクトはどこでもビット一致を主張していない）。

同等性として**機械検査するのは次の 2 つだけ**:

1. **カメラ契約**: C++ の `synthesize_single_view_gauge` が返す `camera_angle_x` / `mesh_scale` /
   `transform_matrix` が、JS の `makeSingleViewTransforms` と同一 FOV 集合で一致する（D9）
2. **前処理の幾何**: C++ / Python / JS のクロップが同一入力に対し同じクロップ矩形・同じ出力サイズを返す（D9）

それ以外（IoU、頂点数、生成時間）はサーフェスごとの実測として別々に記録する。

## 3. 設計判断

### D1: SV の 1 フレーム gauge カメラは C++ に実装する

`include/transforms_json.h`:

```cpp
constexpr float SINGLE_VIEW_DEFAULT_FOV = 0.3490658503988659f;  // 20 deg
constexpr float SINGLE_VIEW_MESH_SCALE  = 1.0f;
// fov_rad は 0 < fov < pi。image_file は transforms 内の file_path になる。
bool synthesize_single_view_gauge(const std::string& image_file, float fov_rad,
                                  TransformsFile& out, std::string& error);
```

`web/app/single_view.js` と同一の式（`distance = 1 / (2 * mesh_scale * tan(fov/2))`、
`mesh_scale = 1.0` 固定、transform_matrix は front 相当）。JS 実装はブラウザ経路の都合で残すが、
D9 で一致を機械検査する。TS 側には新規実装しない。

**枚数から family を推測しない**（A1）。`pixal3d_load_input_views()` は呼び出し側が渡す
明示のモードで分岐する:

- `sv_image` が設定されている → gauge（画像 1 枚。1 枚でなければエラー）
- `views` かつ transforms.json 無し → canonical rig（ちょうど 4 枚。それ以外はエラー）
- `views` かつ transforms.json あり → 従来どおり

CLI の `--sv-image` は、クロップ済み `input.png` と合成 `transforms.json` を
**`<出力GLBのstem>.svviews/` へ書いて残す**（消さない）。A10/A11 の IoU ゲートが
この同じディレクトリを入力に取るため、staging を一時ディレクトリにして消してはいけない。
サーバの `/generate-sv` は従来どおり応答後に staging を消す（サーバ内部パスを外へ出さないため）。

### D2: pre-matted RGBA クロップの完全仕様（C++ 実装の正本）

Python / JS の**実挙動**（`tools/run_pixal3d_estimated.py:61-89`、`web/app/single_view.js:80-113` を
実読して確定）を次のとおり仕様化する。**「クロップ後に 1024 へ縮小」ではない**（A5）:

1. RGBA へデコードする
2. **alpha の最小値が 255 なら拒否**（`input image has no real alpha matte`）、
   **alpha の最大値が 0 なら拒否**（`fully transparent`）
3. `scale = min(1.0, 1024 / max(w, h))`。`scale < 1` のときだけ**画像全体**を
   `(max(1, floor(w*scale)), max(1, floor(h*scale)))` へ縮小する
4. `mask = alpha > 0.8*255` の bbox を取る（両端含む `x0,y0,x1,y1`）。空なら拒否
5. `cx = (x0+x1)/2`、`cy = (y0+y1)/2`、`span = max(x1-x0, y1-y0)`
6. `crop_size = max(2, floor(span*1.1))` → `half = max(1, crop_size/2)` → `crop_size = 2*half`
7. `left = floor(cx-half)`、`top = floor(cy-half)` の正方で切り出す。
   **画像外は透明 (0,0,0,0) でパディングする**（PIL `crop` / canvas `drawImage` と同じ）
8. 出力は PNG RGBA。**長辺は 1024 を超えうる**（最大 `2*floor(1.1*1023/2)` = 1124。
   実際に公式 Belle 入力で 1124² が出ている）

既知の差分（仕様化して残すもの）:

- **拒否条件は 3 実装で食い違っており、`< 250` に揃える**（2026-09-19 実測で v3 から方針変更）:
  - `src/pixal3d_input.cpp:10 load_rgba` … `alpha < 250` の画素が 1 つも無ければ
    「real alpha 無し」として**後段が拒否する**
  - `web/app/single_view.js:93` … 同じく `alpha < 250`
  - `tools/run_pixal3d_estimated.py:56` … `min(alpha) == 255` のときだけ拒否（`< 255` 相当）
  新しい C++ クロップは **`< 250`（既存 C++ ローダ・JS と同じ）** を採る。Python 側（`< 255`）に
  合わせると、クロップが通した画像を同じバイナリ内の `pixal3d_load_input_views` が
  「has no real alpha channel」で弾く自己矛盾が起きるため。外れ値である
  `tools/run_pixal3d_estimated.py` を `< 250` へ揃え、3 実装を一致させる
  （Python 側だけ受理範囲が狭まるが、狭まる分は「直後に C++ が弾いていた入力」なので実害は無い）
- **リサンプラ**: Python=LANCZOS、JS=canvas、C++=stb_image_resize2。画素値は一致しない。
  D9 はクロップ矩形・出力サイズを完全一致で、画素は許容差つきで比較する

### D3: モデルセットは MV=`pixal3d-f16 v1` / SV=`pixal3d-sv-q8_0 v1` の 2 ディレクトリ（配置契約を確定）

9 ファイル中 5 本は family によらず同名で f16 と q8_0 は中身が違うため、1 ディレクトリに同居できない。

| 項目 | MV（既存） | SV（新規） |
|---|---|---|
| server フラグ | `--models DIR` | `--models-sv DIR`（省略可） |
| Studio config キー | `modelsDir`（既存） | `modelsDirSv`（新規・省略可・既定 `""`） |
| managed root（通常） | `<local-data>/trellis-studio/models` | `<local-data>/trellis-studio/models-sv` |
| managed root（portable） | `<exe>/models` | `<exe>/models-sv` |
| installer フラグ | `--model-manifest` / `--model-base-url` | `--model-manifest-sv` / `--model-base-url-sv` |

旧 config の移行（A2）: `modelsDirSv` が無い既存 `config.json` は**そのまま有効**。
`serde(default)` で空文字になり、SV は "not configured" として扱う。移行処理は書かない（純粋な追加）。

片方だけの状態（A2）:

| 状態 | 挙動 |
|---|---|
| MV だけ導入 | サーバ起動、`/generate-mv` 可、`/generate-sv` は 503 `sv model set is not configured` |
| SV だけ導入 | サーバ起動、`/generate-sv` 可、`/generate-mv` は 503 |
| 両方未導入 | **サーバは起動する**（Studio が設定画面を出せるように）。両 endpoint 503 |
| ディレクトリの family 取り違え（`--models` に sv セット等） | **起動は拒否しない**。当該 endpoint を unavailable にし、`reason` に `model_family mismatch: expected mv, manifest says sv` を出す。MV が正しければ MV は使える |
| 片方が破損（manifest 契約違反・ファイル欠損・サイズ不一致） | その endpoint だけ unavailable。もう片方は影響を受けない |
| SV 導入が途中失敗 | installer は検証成功後に manifest を最後へ置くので、manifest 不在＝未完了として unavailable |
| 生成中に active な models ディレクトリを削除 | 既存 MV と同じ扱い（`model_cache.rs` の削除は manifest 記載ファイルのみ・生成中は削除させない）。SV ルートにも同じ保護を入れる |

endpoint は family を**サーバ起動時の既定から継承しない**（A2 / codex 推奨）。各ハンドラで:

```cpp
p.models = models_mv;  p.pixal3d_weights = "mv"; p.pixal3d_weights_set = true;  // /generate-mv
p.models = models_sv;  p.pixal3d_weights = "sv"; p.pixal3d_weights_set = true;  // /generate-sv
```

「native は parity のため F16」という明文方針からの逸脱を checklist に明記する。根拠の実測:
Q8_0 と F16 の品質差は **検出できていない**（views4-style seed1/2 で IoU 差 +0.0019 / −0.0064、
公式 cyclops で 0.0004。F16 自身の seed 間分散 0.0092 より小さい）。**これは同等性の証明ではない**
（2 入力 × 少数 seed で差が見えなかった、まで）。SV の f16 セットは存在せず、作るには 12.7 GiB 級の
変換・検証・公開が要るため今回の範囲外（ユーザー決定）。

### D4: `POST /generate-sv`（fail-closed 契約を明文化）

`/generate-mv` に 1 視点を混ぜない（mesh_scale 必須・4 枚前提という別契約を緩めないため）。

```
POST /generate-sv   multipart/form-data
  許可フィールドは以下の whitelist のみ。未知フィールドが 1 つでもあれば 400
    image      必須。PNG（magic 8 バイト検査）。<= 64 MiB、デコード後 <= 64 Mpixel
    fov        任意。ラジアン。既定 0.3490658503988659。strtod 全体消費 + 有限 + 0 < fov < pi
    seed       任意。strtoul 全体消費、<= UINT32_MAX
    resolution 任意。**1024 のみ**（D10）。他は 400
    uv         任意。"xatlas" | "box" のみ
  → 200 model/gltf-binary / 4xx application/json {"error": ...}
```

明示的に拒否するもの（400）: `mesh_scale`（SV は gauge 固定 1.0）、`transforms`、`view*`、
`num_views`、`band`、`webp`（SV では既定固定）。

数値パースは新しい strict ヘルパ（全体消費 + 有限 + 範囲）を作り、**既存の
`apply_common_overrides` も同じヘルパへ差し替える**。`seed=abc` が黙って 0 になる挙動が
400 に変わるので、リリースノートに**挙動変更**として記載する（A6）。

### D5: Studio は 3 モードを明示する（既存 UI を消さない）

`app/index.html` の左パネル先頭にモードセレクタを置く:

| モード | 入力 | 送信先 |
|---|---|---|
| `TRELLIS.2 (single image)`（既存・既定） | 画像 1 枚 | `POST /generate` |
| `Pixal3D SV (single image)`（新規） | 画像 1 枚 + FOV | `POST /generate-sv` |
| `Pixal3D MV (multiview)`（既存） | 4 枚以上 + transforms.json（任意） | `POST /generate-mv` |

既存 TRELLIS.2 UI は**残す**（A3）。よって gallery のレコード形式・出力ファイル名・設定項目は
変更しない。gallery には任意キー `mode`（欠落時は `"trellis2"` とみなす）だけを足し、
IndexedDB の `DB_VERSION` は上げない（既存レコードはそのまま読める）。

MV パネルの変更: `transforms.json` を**任意**にする。無い場合は

- ちょうど 4 枚であること
- 明示 `mesh_scale`（現行と同じく推測しない）
- 並び順 front / right / back / left を**ユーザーが確認するチェックを必須**にする（R4）

SV パネル: 画像 1 枚、alpha プリフライト、FOV 入力（既定 20°、`0 < fov < 180°`）、
`/capabilities` が `sv.available=false` なら Generate を無効化し `reason` を表示する。

### D6: `GET /capabilities`（`/health` は変更しない）

`/health` は変更しない。`app/src/api.ts:20` が本文を `=== "ok"` で厳密比較しており、
JSON 化すると既存 Studio が即オフライン判定になる。

```json
{"busy":false,"completed":3,
 "mv":{"configured":true,"available":true,"model_set":"pixal3d-f16","version":"v1","model_family":"mv"},
 "sv":{"configured":true,"available":false,"reason":"missing model file: pixal3d_tex_flow_1024_sv.gguf"}}
```

`busy` / `completed` は D11 の「Stop waiting 後にいつ Generate を戻すか」の判定に使う。

`configured` と `available` を分ける（A4）。**`available=true` の条件を凍結する**:

1. ディレクトリが設定されている（`configured`）
2. `pixal3d-models.json` が読めて JSON として妥当
3. **`web/app/model_family.js` と同一の manifest 契約**を C++ で実装して合格すること
   （明示 family と flow 名からの推定の不一致を拒否 / 既知 name は固定 role・required /
   name・role の重複を拒否 / family の必須 9 name・9 role が揃う）
4. 9 ファイルが実在し、**サイズが manifest と一致**する
5. endpoint が期待する family と manifest の family が一致する

SHA256 の再計算はしない（12.7 GiB を毎回読むことになる）。SHA256 検証は installer の
`--model-manifest` / `--verify-models` の責務で、manifest がディレクトリに在ること自体が
「検証済みで完全」の印という既存の契約を踏襲する。この線引きを `/capabilities` の
ドキュメントに明記する。

旧サーバ（`/capabilities` 404）→ Studio は SV モードを無効化し「この runtime は SV 非対応」と表示する。

### D7: installer（2 セット対応）

`--model-manifest-sv PATH|URL` / `--model-base-url-sv URL`（PowerShell: `-ModelManifestSv` /
`-ModelBaseUrlSv`）。検証ロジックは既存と同一（サイズ + SHA256 完全一致、検証後に manifest を
最後にコピー）。`--verify-models` は設定されている両ディレクトリを検証する。
SV を指定しない既定の挙動は変えない。installer は config に `modelsDirSv` を書く。

必要空き容量（B 指摘）: 導入前に「manifest 合計バイト + 10%」の空きを検査し、足りなければ
ダウンロード前に失敗させる。`.part` は同一ディレクトリに置き、失敗時は削除する（既存踏襲）。

### D8: バージョンと配布

- numeric version **0.10.0** を 5 ファイルで揃える: `app/package.json`、`app/package-lock.json`、
  `app/src-tauri/tauri.conf.json`、`app/src-tauri/Cargo.toml`、`app/src-tauri/Cargo.lock`

  prerelease 識別子を拒否するため）
- リリースノートに必ず書く: MV=f16 / SV=q8_0 の 2 セット、SV は任意導入、SV は 1024 のみ、
  Cancel は「待機の中止」であること、`seed` 等の不正値が 400 になる挙動変更、
  macOS/Apple Silicon のみ E2E 検証済み、署名は ad-hoc、**loopback 以外での公開は非推奨**

### D9: 実装の一致検査

- `synthesize_single_view_gauge`（C++）vs `makeSingleViewTransforms`（JS）:
  FOV = {20°, 30°, 45°, 1e-3 rad, π−1e-3} で `camera_angle_x` / `mesh_scale` /
  `transform_matrix` 16 要素が相対誤差 1e-6 以内で一致。固定 JSON フィクスチャを
  `tests/fixtures/sv_gauge.json` に置き、C++ テストと node テストの双方が読む
- クロップ（C++ / Python / JS）: 共通フィクスチャ画像 6 枚
  （1024 超、1024 以下、bbox が奇数、bbox が画像端に接する、foreground 1 px、
  最小 alpha が 250〜254＝3 実装とも「real alpha 無し」で拒否すること）に対し
  - クロップ矩形 `left/top/size` と出力サイズが**完全一致**
  - alpha マスクの IoU >= 0.99、premultiplied RGB の MAE <= 2/255

### D10: SV の解像度は 1024 のみ（API・UI 両方）

API が 1536 を受けるのに実機検証しない、という矛盾（A9）を「受けない」で解消する。
`/generate-sv` は `resolution != 1024` を 400 にし、UI は 1024 だけを出す。
CLI の `--sv-image` も 1024 のみ許可する。MV は現状どおり 1024/1536 の両方を受ける
（1536 が未検証なのは 0.9.0 から変わらない既存状態）。

### D11: Cancel は「待機の中止」に限定し、サーバに busy を申告させる

現在の AbortController はクライアントの待機を止めるだけで、サーバの `trellis_run()` は
mutex 内で走り続ける（A7）。25〜35 分の処理なので次のとおりにする。

- ボタン名を **`Stop waiting`** にする（既存 MV パネルも同じ名前に揃える）
- 押した後は「サーバは生成を継続中」と表示する

**再有効化の判定手段を作る（round 2 の残指摘）**。「待機をやめた後にサーバの完了を
検知できないので Generate をいつ戻すか決められない」という指摘は正しいので、
サーバ側に busy を持たせる:

```cpp
// trellis-server.cpp: 生成は既に gen_mu で直列化されている。その外側で状態を公開する。
std::atomic<bool>        g_busy{false};        // 生成中
std::atomic<uint64_t>    g_completed{0};       // 完了した生成の通算本数（成功・失敗を問わず）
```

`/capabilities` に `{"busy": bool, "completed": <uint64>}` を足す。Studio は既に 4 秒周期で
`/health` をポーリングしているので、同じ周期で `/capabilities` も読む:

- Generate が押せる条件は `busy === false`
- `Stop waiting` 時点の `completed` を記憶し、`busy===false && completed > 記憶値` になったら
  「前の生成は終わりました」と表示して Generate を戻す
- `/capabilities` を持たない旧サーバでは、従来どおり待機中止＝即再有効化（挙動を変えない）

これは複数ウィンドウ・複数クライアントから同じサーバを叩いたときの「他が生成中」表示にも使える。
真の中断（`trellis_run` への協調的 cancel）は本リリース範囲外で、別 issue を立てる。
