## 概要

RoPE レイアウト修正（d4ffdf4）後、Metal の flow DiT forward で最大の単一コストは FlashAttention
（Shape-1024 の node pass で 11.7 s / 22.5 s = 52%、`docs/results/2026-09-20-metal-flow-profile.md` §3）。
既存の `TRELLIS_FA_FAST=1`（K/V を BF16 でなく F16 にキャストする A/B 経路）が Metal で速い可能性がある一方、
`src/dit.cpp::sdpa` のコメントは「HR 活性化が F16 の範囲（±65504）を超えるので BF16+F32 累積が既定」と述べている。
本設計は (1) Metal カーネルの実際の数値仕様を確定し、(2) 速度・範囲・品質の 3 つの計測を定義し、
(3) ゲートを通った場合に限り **Metal だけ** 既定を切り替える（CUDA / Vulkan / WebGPU は不変）ための手順を決める。

## 背景: Metal カーネルの数値仕様は CUDA の前提と逆（ソース確認済み、2026-09-20）

`sdpa` の BF16 既定は CUDA の挙動（BF16 K/V を内部で F16 に変換、`set_prec(F32)` で VKQ を FP32 累積）から
来ている。Metal backend（`thirdparty/ggml/src/ggml-metal/`、v0.15.1+10 `trellis-patches`）を読むと:

| 事実 | 根拠 |
|---|---|
| Metal backend は `ggml_flash_attn_ext_get_prec` / `GGML_PREC` を**一度も読まない**。`set_prec(F32)` は Metal では no-op | `grep -rn prec ggml-metal/` にヒット無し（CUDA は `fattn.cu:585`、`fattn-wmma-f16.cu:571` で読む） |
| 非 vec カーネル（Lq ≥ 20 で選択。`ggml-metal-ops.cpp:2516` `use_vec = ne01 < 20`）の O 行列 `so` は `threadgroup o_t*` で、KV ループ（`ggml-metal.metal:6028` `for ic0`）をまたいで保持され、毎タイル `so4 *= ms`（L6291）で再スケール → `simdgroup_load / multiply_accumulate / store`（L6313, 6335, 6373）で加算される | `ggml-metal.metal:5939` |
| **BF16 K/V カーネル（`FA_TYPES_BF`、L6565）: q = bfloat（仮数 7 bit）、K/V = bfloat、QK = float、softmax = float、`o_t` = **half**** | L6566–6571 |
| **F16 K/V カーネル（`FA_TYPES`、L6556）: q = half（仮数 10 bit）、K/V = half、QK = float、softmax = float、`o_t` = **float**** | L6557–6562 |
| F32 K/V カーネル（`FA_TYPES_F32`、L6574）: q = half、K/V = float、`o_t` = float | L6575–6580 |
| Q は `sq4[...] = (q4_t) q4[i]`（L5987）で **scale を掛けずに** q_t に変換され、scale はスコアに float で掛かる（L6259） | |
| pipeline 名は `kernel_flash_attn_ext_<K/V type>_dk128_dv128`（`ggml-metal-device.cpp:1390`。head_dim = 128、`include/dit.h:17`）。BF16 kernel は `has_bfloat`（M4 Max は true）のときだけ選ばれる | |

したがって Metal では、現在の既定（BF16 K/V + 無視される `set_prec`）は
「q を 7 bit 仮数に落とし、self-attention では ~17.6k 項（HR）の softmax 加重和を **half で累積**」しており
（cross-attention は Lk = 5 なので累積長の問題は無く、q/K/V の仮数差だけが効く）、これは `sdpa` コメントが
CUDA TILE カーネルの不具合として説明している「F16 累積の停滞（小さい加数が丸め落ちて低バイアス）」と
同じ機構である。F16 K/V に切り替えると q が 10 bit 仮数・出力累積が float になる。

**新たに増えるリスクは Q / K / V の F16 範囲超え（|x| > 65504）**で、3 つの扱いが違う:

- Q / K は `rms_gamma`（head_dim 単位の RMSNorm × gamma、`dit.cpp:326-327, 345-346`）を通ってから RoPE
  （ノルム保存の回転）に入るので、head_dim = 128 では要素の上界が `sqrt(128) × max|gamma| ≈ 11.31 × max|gamma|`
  で静的に抑えられる（overflow 境界 max|gamma| ≈ 5790、8× headroom 境界 ≈ 724）。実測（`tools/fa_gamma_bound.py`、
  q8_0 MV v1）: max|gamma| は SS 8.47 / Shape-512・1024 18.20 / Texture 5.31 → 上界 95.8 / 205.9 / 60.1、
  **F16 headroom 684× / 318× / 1091×**。これは数学的上界であり、RoPE の cos/sin 誤差や量子化重みの影響は
  実測（R）で併せて確認する。なお F32 K/V カーネルでも **Q は half に落ちる**（`FA_TYPES_F32` の q_t = half）ので、
  Q の範囲は K/V 型に依らず F16 の制約を受ける（現行 BF16 既定だけが例外で q = bfloat）。
- **V には RMSNorm が無い**（self / cross とも）。`V_SCALE = 1/256` は閾値を 65504 × 256 ≈ 1.68e7 へ広げるだけで
  保証ではなく、**V の範囲は実入力の動的計測（R）でしか裏付けられない**。

## 仮説

H1（速度）: Metal では F16 K/V の方が BF16 K/V より FA が速い（half8x8 simdgroup 演算がネイティブ、bfloat8x8 より
変換コストが少ない）。効果量は未知（FA は forward の ~50% なので、FA が 1.3× なら forward で ~1.13×）。

H2（数値）: Metal では F16 K/V の方が `--no-fa`（exact SDPA、oracle）に近い（出力累積 float、q 10 bit）。
「F16 が危険」は CUDA の前提であり、Metal では BF16 の方が精度面で不利。

H3（範囲）: Q / K は RMSNorm 由来の静的上界で F16 範囲に収まり（R1 で確認済み: headroom ≥ 318×）、V は V_SCALE で
収まる。V は静的に抑えられないので、実入力 2 種以上で max|Q|, max|K|, max|V/256| の headroom（65504 / max）を測る。

## 提案

### 1. K/V 型を明示する CLI フラグ `--fa-kv {auto,bf16,f16,f32}`（既定 `auto`）

- `include/dit.h`: `enum FaKv { AUTO, BF16, F16, F32 }`、`extern int g_fa_kv`（要求値、`g_no_fa` と同じ置き方）、
  `dit_fa_kv_parse()`、`dit_fa_kv_effective(ggml_backend*)`（AUTO の解決）、`dit_fa_kv_name()`。
- `src/trellis_args.cpp`: `--fa-kv <t>` の parse（不正値は **起動失敗**、silent fallback しない）と help。
- **優先順位**（固定）: `--fa-kv` > `TRELLIS_FA_KV` > `TRELLIS_FA_FAST=1`（= f16 の旧名。`docs/spec/29-perf-profile.md`、
  `docs/PIXAL3D_WEBGPU_OP_GAP.md`、`README.md:345` が参照するので残す）> backend 既定。
- **解決の場所は `build_dit_dense`（`src/dit.cpp`）の入口 1 箇所**: `const Model& m` から `m.backend` を見て
  `dit_fa_kv_effective()` を呼び、その graph の型として file-static に固定する（`g_cast_f32 = p.cast_f32` と同じ流儀）。
  `DitRunner` / WASM / 全テスト / server はすべて `build_dit_dense` を通るので網羅され、同一プロセスで backend が
  混在しても graph ごとに正しく解決される。`DitRunner` 構築時に
  `dit graph: FlashAttention K/V=<effective> (--fa-kv <requested>)` を 1 行印字し、`--no-fa` 時は FA 自体を使わない
  ので K/V 型を印字しない（`exact SDPA (--no-fa)` のログが既にある）。server は同じログを起動時と各リクエストで出す
  （`/capabilities` への追加は別 issue）。
- **backend 既定（`auto`）は本計測が終わるまで全 backend で bf16**（現状の挙動と完全一致）。ゲート通過後に
  Metal だけ f16 へ切り替える（別 commit）。backend 行列:

  | backend | auto | 明示 bf16 | 明示 f16 | 明示 f32 |
  |---|---|---|---|---|
  | Metal (has_bfloat) | ゲート前 bf16 / 後 f16 | 実行 | 実行（prec 無視、O=float） | 実行（q は half） |
  | Metal (bf16 非対応: M1) | 同上（bf16 は `supports_op` で弾かれ CPU fallback。従来からの挙動。README の M1 向け `TRELLIS_FA_FAST=1` 注記は `--fa-kv f16` に書き換える） | 同左 | 実行 | 実行 |
  | CUDA | bf16（現状維持） | 現状 | 旧 FA_FAST と同一（f16 累積） | 未検証（`supports_op` 次第） |
  | Vulkan | bf16（現状維持） | 現状 | 旧 FA_FAST と同一（RADV crash 記録あり） | 未検証 |
  | WebGPU | FA は dtype gate で不可 → `--no-fa` 経路（現状維持） | 同左 | 未検証 | 未検証 |
  | CPU | bf16（現状維持） | 実行 | 実行 | 実行 |

  「未検証」は本 issue の範囲外（Metal の A/B が目的）で、明示指定は利用者責任。unsupported なら従来どおり
  `check_graph_supported` が構築時に警告/失敗する。
- **`set_prec(F32)` の条件は変えない**（bf16 / f32 のとき付け、f16 は付けない）。これで CUDA / Vulkan の
  `TRELLIS_FA_FAST` の意味（f16 K/V + f16 累積）は完全に据え置き、Metal は prec を無視するので f16 でも O=float。
  累積 policy の変更は別 issue（`--fa-accum`）に切り出す。
- `sdpa` のコメントを「CUDA の根拠」と「Metal の実測仕様」に分けて書き直す。

### 2. 範囲計測 `TRELLIS_DBG_FA_RANGE=1`（デバッグログのみ、挙動不変）

- `sdpa` は `build_dit_dense` が file-static に置いた `inter` と attention 名（`blocks.<i>.self_attn` /
  `blocks.<i>.cross_attn.cross_attn_block`）を使い、有効時は cast **前**の F32 テンソル `qf`（[hd, Lq, nh]）、
  K（permute+pad 後）、V（`V_SCALE` 適用後）を `<name>.fa_{q,k,v}` として登録する。
- `DitRunner`（`flow_runner.cpp`）は `dbg_nan_` と同様にこれらを output に固定し、forward ごとに role（self / cross）×
  operand（Q / K / V·V_SCALE）の `max|x|`（とその block）、F16 headroom = 65504 / max、**非ゼロ要素のうち** F16 の
  正規化数下限（6.1e-5）未満の割合 `sub` と最小 subnormal（6e-8）未満（f16 で 0 に落ちる）の割合 `tiny`、nonfinite 数を
  印字する（padding の 0 は分母から除く。0 は f16 でも厳密に 0）。
- メモリ（head_dim 128、N = 17612、pad 後 17664、12 heads、F32）: self の Q / K / V が各 ~103 MiB × 30 block ≈ 9.1 GiB、
  cross の Q が 30 × 103 MiB ≈ 3.0 GiB、cross K/V は Lk = 5 で無視できる → **約 12.1 GiB** を output として固定
  （gallocr が再利用できなくなる）。M4 Max 64 GB では重み 2.6 GB + 通常の活性化 ~2 GB を足しても収まる見込みだが、
  **pilot（forward 1 回）で `check_device_budget` の実測 alloc を印字して予算内であることをゲートにする**。
  ホストへの読み戻しは forward あたり ~12 GiB の memcpy + 走査で数秒、1 flow（~20 forward）で 1〜2 分の追加。
  既定 off のときはグラフに一切変化なし。

### 3. flow 出力と HR 入力のダンプ `TRELLIS_DUMP_SLAT=<dir>`（デバッグ、挙動不変、MV 経路）

- `trellis_cli.cpp::trellis_run_mv` の各 flow 出力: `ss_latent` / `ss_logits` / `ss_coords` / `lr_slat` / `hr_slat` /
  `tex_slat` を `<name>.bin`（i32 N, C, has_coords; i32 coords[N*3]; f32 feats[N*C]）に書く。`.part` に書いてから
  rename（途中終了の半端ファイルを残さない）。`manifest.json`（時刻・seed・入力・重みディレクトリ・res・`--no-fa`・
  要求 `--fa-kv`・gss/gsh）を同じディレクトリに置き、backend / effective K/V 型 / 時間は run log（同ディレクトリに保存）
  で持つ。
- 同時に **HR flow の実入力を `trellis-test-pixal3d-slat-sample` の fixture 形式（.npy）で書く**: `hr_coords`
  [N,4]、`shape_cond_global` [1,Lc,1024]、`shape_cond_proj` [N,2048]、`shape_noise` [N,32]、`shape_norm_mean/std`、
  `shape_sampler_params`、および `tex_*` 一式と `f32_tex_concat_cond`（= 正規化 Shape-1024 SLAT）。これで
  **DINOv3 / NAF / cascade を再実行せずに、実 conditioning のまま seed（`--noise`）と attention 設定だけを変えて
  HR flow を再サンプルできる**（tex: 12 forward ≈ 3 分、shape_hr: CFG 込み ~20 forward ≈ 5 分）。
  既存 `~/nfs/weights/pixal3d/synth_tex_fixture` は cond が N(0,1) の合成物で、範囲・品質の判定には使わない。
- 比較スクリプト `tools/compare_slat_dumps.py`（numpy のみ）: `--ref <oracle dir>` を基準に各候補の
  `max|d|`, `rms(d)`, `rms(d)/rms(ref)`, mean(d), nonfinite を印字。coords は集合として比較し、順序だけ違えば
  座標で join、集合が違えば **voxel Jaccard / 対称差** を印字して要素比較は拒む。

チャンク単位に実体化する経路で、PyTorch golden との一致が既存テストで確認されている
（`sdpa` コメント: 「this is the path the golden-tensor test matches to 8e-5 on the output mean」、`trellis-test-shape-flow`）。
FA より真値に近い根拠はこれと「中間を一切 16 bit に落とさない」ことで、倍精度の独立参照は本 issue では作らない
（差分の大小関係の判定に必要なのは「FA 2 腕より高精度な共通参照」であり、それは満たす）。

## テスト計画（受け入れ基準、着手前に凍結）

1. **NaN/Inf ゼロ**: R の 2 入力 × 全 flow で nonfinite = 0（`[stats]` 行と `[fa-range]` の `bad`）。
2. **範囲 headroom ≥ 8×**: 全 forward・全 role で `65504 / max|Q|`, `/ max|K|`, `/ max|V/256|` ≥ 8。`tiny`（f16 で 0 に
   落ちる非ゼロ要素）の割合は報告のみ（ゲートにしない: 値が 6e-8 未満の要素は q·k / softmax·V への寄与も同程度に小さい）。
3. **数値**:
   - 3a（Q1、SS latent、要素比較）: `rms(f16 − ref) ≤ rms(bf16 − ref)` かつ `max|f16 − ref| ≤ 1.5 × max|bf16 − ref|`
     （max は外れ値依存なので安全ゲート扱い）。
   - 3b（Q1、HR）: coords 集合が一致すれば 3a と同じ基準。不一致なら voxel 集合で
     `Jaccard(f16, ref) ≥ Jaccard(bf16, ref) − 0.005` かつ **絶対下限 `Jaccard(f16, ref) ≥ 0.95`**（両候補が共に悪い
     場合を除外）。GLB は既存ゲート `tools/silhouette_iou.py --res=256`（`~/nfs/pixal3d-desktop-0.10.0-acceptance/
     2026-09-19/gate.sh` と同じ呼び方）の **入力 4 view に対する mean silhouette IoU** で
     `IoU_f16 ≥ IoU_bf16 − 0.005` かつ `IoU_f16 ≥ 0.85`（既存ゲートの床）かつ `scale_error ≤ 0.05`（既存）、V/F は
     `|V_f16/V_bf16 − 1| ≤ 0.05`（報告値。超えたら 6 視点レンダで原因を特定）、6 視点レンダ（`render6.py`）を並置して
     破綻（欠け・突起・非対称）の有無を目視（目視は報告事項で、ゲートは Jaccard / IoU）。0.005 は同一条件再実行対
     （bf16 の 2 run）の IoU 差を先に測り、それより小さければその実測値に置き換える。
   - 3c（Q2、paired n≥5）: seed ごとの `d_k = log(rms_err_f16,k / rms_err_bf16,k)` の平均 `d̄` と標準誤差から片側 95% CI
     の上限を出し、**上限 < 0 なら「f16 が bf16 より参照に近い」**、上限 < log(1.05) なら「同等（劣化なし）」、
     それ以外は「判定不能（既定は変えない）」。同一腕再実行対のノイズ床 `|d_noise|` が `|d̄|` と同程度なら差を解釈しない。
4. **速度**: S の paired ratio `t_bf16 / t_f16` の 95% CI が全体で 1 を超える（各 flow。Shape-512 は 6 block、
   HR 2 flow は 5 block = 各腕 5〜6 標本）。超えなければ既定は変えない（数値が良くても本 issue の目的は速度なので、
   「精度改善のみ」は結果として記録し別 issue にする）。
4b. **op 単体の参照性（O）**: 両 backend で exact の rel_rms < 1e-5、全構成 nonfinite = 0。
5. **holdout E2E**: 1〜4 を通ったら Metal auto = f16 の E2E 1 本を **R/Q に使っていない入力・seed**（例: ZZZ SV 入力、seed 7）
   で走らせ、NaN/Inf ゼロ・GLB 出力・6 視点レンダで破綻なし（IoU の定量ゲートは、seed 間差の分布を持たないので
   置かない。報告のみ）。
6. 既存テスト（backend / 期待値を明記）:
   - `trellis-test-rope-layout`（Metal、exit 0、`max|d| < 1e-5`）— 本変更で RoPE は触らないが FA 経路の回帰確認。
   - `trellis-test-dit-bench <shape_512> 256 2 -1`（CPU）を `TRELLIS_FA_KV=bf16|f16|f32` × `TRELLIS_DBG_FA_RANGE=1` で

     `dit graph: FlashAttention K/V=` の行で確認する。
   - `trellis-test-shape-flow` / `trellis-test-pixal3d-slat-flow` は参照テンソル（`tools/ref_*.py`、この Mac に無い）が

## 再確認後の対応（codex 承認条件 4〜7）

| 条件 | 対応 |
|---|---|
| 4（12 GiB の全テンソル固定） | `TRELLIS_DBG_FA_RANGE=<q/k/v の部分集合>` で probe する operand を選べるようにした（`v` だけなら ~3 GiB。V が唯一静的上界の無い operand）。E2E の pilot で `check_device_budget` が超過を投げたら `v` だけで再走する。graph 内縮約（max-abs の reduce op が ggml に無い）や block 単位 runner は、この一回限りの計測には過剰と判断 |
| 5（`--no-fa` の妥当性） | `trellis-test-fa-oracle` を追加（上表 O）。attention op を float64 ホスト参照と比較し、exact の rel_rms < 1e-5 を機械判定にする。実測（CPU backend、N=64）: exact 1.4e-7 / FA bf16 2.8e-3 / FA f16 2.9e-4 / FA f32 3.5e-7 |
| 6（n） | 品質: R の 2 入力目（`belle` 単一画像 + MV 重み V=1、`~/nfs/pixal3d-sv-acceptance/2026-09-17-pr13/sv_views`、seed 42）の E2E からも実 fixture を書き出し、Q2 を **2 クラス × 5 seed = 10 対**にする。速度: HR の block を 5 に増やす（各腕 5 標本）。Shape-1024 と Texture の flow は別々に判定する |
| 7（GLB 閾値） | テスト計画 3b に絶対下限（Jaccard ≥ 0.95、IoU ≥ 0.85、scale_error ≤ 0.05）と paired マージン（0.005、再実行対の実測で置換）を数値で置いた |

## 代替案

- **BF16 K/V + float O（Metal カーネルの `FA_TYPES_BF` の o_t を float にするパッチ）**: 因果の切り分け（改善が q/K の
  仮数差か O 累積か）には有用だが、ggml fork のパッチが増える（`PIXAL3D_UPSTREAM_POLICY.md`）。f16 で速度と数値の
  両方が取れるなら不要。f16 が速くない・または数値が悪い場合の第 2 候補として結果文書に残す。
- **Q または K を 2^-k 倍して score scale を 2^k 倍する**（cast 前の実数演算では同値。cast 誤差は変わる）: 範囲 headroom が
  薄い場合の対処。R1 の上界から不要の見込みで、R の結果で必要になったときだけ実装する。
- **F32 K/V**: K/V の cast 範囲リスクを除く比較腕（Q は half のまま）。速度が f16 と同等なら K/V 側の安全策になる。
- **何もしない**: FA が forward の 52% なので、他の候補（#29 decimate、#31 f16 GEMM）より効果の上限が大きい。
