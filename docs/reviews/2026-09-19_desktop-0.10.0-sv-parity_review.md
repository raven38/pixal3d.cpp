### レビュー結果サマリー

- 判定: **差し戻し**
- A（実装を止める指摘）:

  - **SV の入口と内部モード指定が未決です。** Q2 は CLI 契約、`TrellisParams`、入力分岐、A11 を直接変えます。`--sv-image PATH` を採用し、`sv_image` を明示状態として持たせる案を推奨します。画像枚数から family を推測してはいけません。現状の `--pixal3d-weights` は `--views` 必須です（[trellis_args.cpp](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/src/trellis_args.cpp:173)）。
  - **MV/SV の2ディレクトリ導入契約が不足しています。** `--models-dir-sv`、既定配置、portable 配置、`modelsDirSv` の旧設定移行、片方だけ導入・検証・削除する場合の挙動が未定です。D7 の manifest/base URL だけでは SV の保存先を決められません。
  - **既存の単一画像 TRELLIS.2 UIを残すか置き換えるかが未決です。** 現在の画面には `/generate` 用の単一画像 UI、MV UI、gallery が共存しています（[index.html](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/app/index.html:28)）。D5 の二択モードにすると、既存機能の削除、gallery の記録形式、設定項目、互換性が変わります。
  - **`/capabilities` の `available` の意味が弱すぎます。** `model_family` だけ読んでも、必須9 role、family とファイル名の一致、欠損、サイズ不一致を検出できません。Web 側には既に厳密な family/name/role 契約があります（[model_family.js](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/web/app/model_family.js:49)）。C++ サーバでも同じ契約を実装し、`available=true` の判定条件を固定してください。
  - **C++ クロップ仕様が既存実装と一致していません。** D2 は「クロップ後に長辺1024へ縮小」と読めますが、Python/JS は「元画像全体を長辺1024以下へ縮小→bbox→1.1倍クロップ」で、余白により最終画像が1024を超える場合があります（[run_pixal3d_estimated.py](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/tools/run_pixal3d_estimated.py:61)、[single_view.js](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/web/app/single_view.js:80)）。処理順、丸め、補間、境界外透明パディングまで仕様化してください。
  - **`/generate-sv` の fail-closed 契約と異常系が不足しています。** 解像度は「1024以上」ではなく `{1024,1536}`、数値は全体消費・有限値検査、許可フィールドは whitelist、画像形式・magic・最大バイト数・最大画素数を定義すべきです。現行共通処理の `atoi` は不正値を黙って受けます（[trellis-server.cpp](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/src/trellis-server.cpp:108)）。
  - **Cancel と同時実行の意味が未定です。** 現在の AbortController はクライアントの待機を止めるだけで、サーバの `trellis_run()` は継続します。25〜35分処理で「Cancel」と表示するなら、真の中断を実装するか、「応答待ちのみ中止・サーバは継続」と明示して再実行を抑止する必要があります。
  - **受け入れ基準が再現可能な形に固定されていません。** A10 は `silhouette_iou.py` に必要な GLB・クロップ済み views directory・合成 transforms の指定がなく、A11 の「一致」に許容差がありません。また Web alpha 同等性を掲げるなら、同一入力を使うクロスサーフェス契約試験か、「API/機能同等であり出力同等ではない」という定義が必要です。
  - **SV 1536 の扱いが矛盾しています。** API は受理する一方で実機検証は除外されています。1024のみを release-supported としてUIで1536を無効化するか、1536の最低限の実機ゲートを追加してください。

- B（後から直せる指摘）:

  - D8 の「4ファイル」は、列挙上は `Cargo.lock` を含めて5ファイルです。
  - 「3重実装」はクロップには正しい一方、カメラ合成は現状 C++/JS の2実装です。
  - Q8_0 と F16 の差が「検出できていない」は妥当ですが、同等性の証明ではないことを明記してください。
  - R2 は実機E2E前だけでなく、installer の必要空き容量、`.part` 用一時領域、失敗後の再開・清掃も扱うべきです。
  - `Access-Control-Allow-Origin: *` と任意 host bind の脅威モデルを記載し、非loopback公開時のGPU DoSリスクを known limitation に追加してください。
  - 影響ファイル一覧に `types.ts`、`settings.ts`、`mv_calibration.ts`、`pixal3d_input.*`、`trellis_args.*`、CMake、portable README、CI の paths filter、release workflow を明記してください。
  - E2E の GLB、6視点画像、IoU montage、ログ、manifest SHA256 の保存先と命名規則をチェックリストに追加してください。

### 詳細フィードバック（観点ごと）

#### 1. 設計の完全性

全体の構成、スコープ、設計判断、受け入れ基準、リスク、代替案は揃っており、方向性は良好です。特に `/health` を維持して `/capabilities` を分離した判断と、MV/SV を別ディレクトリにする判断は妥当です。

ただし、[設計書の未決Q2](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/docs/design/2026-09-19-desktop-0.10.0-sv-parity.md:221) は実装詳細ではなく公開CLI契約そのものです。また以下が未決です。

- `--models-sv` と `modelsDirSv` の既定値・保存先
- 旧 `config.json` の移行
- MVのみ、SVのみ、両方破損時の起動挙動
- 既存 `/generate` UIの存廃
- Cancel の保証
- `available`、`configured`、`verified` の区別
- 1024/1536のサポート境界

この状態では受け入れ基準を本当に凍結できません。

#### 2. 技術的実現可能性

C++へのカメラ合成とクロップ移植、専用 `/generate-sv`、family別モデルディレクトリはいずれも実現可能です。モデルがリクエストごとにロードされるため、family切替のために常駐モデルを複数保持する必要もありません。

ただし「追加コストは無い」は、「追加の常駐VRAM/RAMはない」と限定すべきです。ディスクキャッシュ、Q8/F16の読み込み時間、20.3 GiBのストレージ消費は残ります。

SV endpoint は必ず次を強制設定すべきです。

```text
p.models = models_sv
p.pixal3d_weights = "sv"
p.pixal3d_weights_set = true
```

MV endpoint も同様に `models_mv` と `"mv"` を強制し、サーバ起動時の生成デフォルトから family を継承させない方が安全です。

#### 3. リスク・懸念

重要な異常系は次です。

- `model_family: sv` だが `_mv.gguf` を列挙した manifest
- manifest は正しいが必須ファイルが欠損
- SV導入途中で失敗し、MVだけ正常な状態
- fully transparent、alpha≤0.8のみ、極小foreground、端に接したforeground
- 巨大PNG・展開後巨大画像・非PNGデータ
- `fov=nan`、`inf`、指数表記のoverflow、極端な正数
- `resolution=1024x` や `uv=typo`
- Cancel後に次の生成を開始し、前の処理がmutex内で継続
- 実行中にactive model cacheを削除
- `modelsDirSv` が古い外部パスを指す旧設定

特に CORS `*` のサーバへ長時間GPU endpointを追加するため、loopbackを既定かつ推奨境界として明記すべきです。

#### 4. 影響範囲の網羅性

既存のモデルcacheは単一rootです（[model_cache.rs](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/app/src-tauri/src/model_cache.rs:24)）。単純に `inspect()` の戻り値を配列化するだけでなく、削除時のserver停止判定、外部ディレクトリ保護、portable fallbackも二系統化する必要があります。

また現在の MV API は transforms を必須引数にしています（[api.ts](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/app/src/api.ts:134)）。canonical 4-view 対応では、単に preflight を変えるだけでなく、API型、FormData構築、ドキュメントコメント、UIテストを同時に変更する必要があります。

破壊的変更候補として、既存TRELLIS.2単一画像UI、gallery record schema、出力ファイル名、設定ファイル、installer receiptを明示してください。

#### 5. テスト計画の妥当性

段階順は妥当ですが、次を追加すべきです。

- 実サーバのHTTP契約試験:
  - endpointごとのfamily/model directory強制
  - `/capabilities` の正常・旧サーバ404・不正manifest・欠損モデル
  - 不明フィールド、重複フィールド、不正数値、誤content type
  - opaque、fully transparent、foregroundなし、巨大入力
- 二重installer試験:
  - MVのみ、SVのみ追加、両方検証
  - SV破損時もMVを壊さない
  - family取り違え、混在manifest
  - 旧configからの移行とportable配置
- Tauri lifecycle smoke:
  - dummy serverが `--models-sv` を実際に受け取ったこと
  - `/capabilities` によるUIのenable/disable
- D9:
  - crop矩形だけでなく、alpha mask IoU、premultiplied RGBのMAEなど許容差付き画素比較
  - 1024超、奇数bbox、境界外padding、1px foregroundを含む複数fixture
- 実機:
  - A10の完全なコマンドと入力directory
  - A11の頂点・面数・IoU許容差
  - 6視点画像とmontageの保存パス
  - 同一runtime SHA、manifest SHA、seed、FOV、resolutionの記録

現状の headless smoke はUI操作中心で、実API契約を検証していません（[headless-mv-ui.mjs](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/app/tests/headless-mv-ui.mjs:13)）。

#### 6. 代替案の検討

`/generate-mv` へSVを混在させず、専用 `/generate-sv` とする判断は支持します。familyごとの別ディレクトリも、同名かつ異なる5ファイルがある以上、最も単純で安全です。

未決案については次を推奨します。

- CLI: `--sv-image PATH --fov RAD` を採用する。既存のTRELLIS.2 `--image`、MV `--views` と排他的にし、枚数推論を避ける。
- UI: 現在の単一画像領域を「TRELLIS.2 / Pixal3D SV / Pixal3D MV」の明示的な3モードにするか、TRELLIS.2を廃止するなら破壊的変更として宣言する。
- capability: サーバを唯一の実行可否authorityにする。ただし `configured` と `available` を分け、後者はmanifest契約と必須ファイル確認後だけtrueにする。
- Cancel: 真の中断が今回困難なら、「Stop waiting」に名称変更し、サーバ処理完了までは全モードのGenerateを無効にする。真のCancelは別issue化する。

設計の骨格は良いものの、現状は公開契約と互換性に関わる未決事項が残っているため、実装開始前の差し戻しが妥当です。レビューは読み取りのみで、コード変更やテスト実行は行っていません。

既存のモデルcacheは単一rootです（[model_cache.rs](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/app/src-tauri/src/model_cache.rs:24)）。単純に `inspect()` の戻り値を配列化するだけでなく、削除時のserver停止判定、外部ディレクトリ保護、portable fallbackも二系統化する必要があります。

また現在の MV API は transforms を必須引数にしています（[api.ts](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/app/src/api.ts:134)）。canonical 4-view 対応では、単に preflight を変えるだけでなく、API型、FormData構築、ドキュメントコメント、UIテストを同時に変更する必要があります。

破壊的変更候補として、既存TRELLIS.2単一画像UI、gallery record schema、出力ファイル名、設定ファイル、installer receiptを明示してください。

#### 5. テスト計画の妥当性

段階順は妥当ですが、次を追加すべきです。

- 実サーバのHTTP契約試験:
  - endpointごとのfamily/model directory強制
  - `/capabilities` の正常・旧サーバ404・不正manifest・欠損モデル
  - 不明フィールド、重複フィールド、不正数値、誤content type
  - opaque、fully transparent、foregroundなし、巨大入力
- 二重installer試験:
  - MVのみ、SVのみ追加、両方検証
  - SV破損時もMVを壊さない
  - family取り違え、混在manifest
  - 旧configからの移行とportable配置
- Tauri lifecycle smoke:
  - dummy serverが `--models-sv` を実際に受け取ったこと
  - `/capabilities` によるUIのenable/disable
- D9:
  - crop矩形だけでなく、alpha mask IoU、premultiplied RGBのMAEなど許容差付き画素比較
  - 1024超、奇数bbox、境界外padding、1px foregroundを含む複数fixture
- 実機:
  - A10の完全なコマンドと入力directory
  - A11の頂点・面数・IoU許容差
  - 6視点画像とmontageの保存パス
  - 同一runtime SHA、manifest SHA、seed、FOV、resolutionの記録

現状の headless smoke はUI操作中心で、実API契約を検証していません（[headless-mv-ui.mjs](/Users/s25705/Downloads/pixal3d.cpp-feat-browser-partial-e2e-integrate/app/tests/headless-mv-ui.mjs:13)）。

#### 6. 代替案の検討

`/generate-mv` へSVを混在させず、専用 `/generate-sv` とする判断は支持します。familyごとの別ディレクトリも、同名かつ異なる5ファイルがある以上、最も単純で安全です。

未決案については次を推奨します。

- CLI: `--sv-image PATH --fov RAD` を採用する。既存のTRELLIS.2 `--image`、MV `--views` と排他的にし、枚数推論を避ける。
- UI: 現在の単一画像領域を「TRELLIS.2 / Pixal3D SV / Pixal3D MV」の明示的な3モードにするか、TRELLIS.2を廃止するなら破壊的変更として宣言する。
- capability: サーバを唯一の実行可否authorityにする。ただし `configured` と `available` を分け、後者はmanifest契約と必須ファイル確認後だけtrueにする。
- Cancel: 真の中断が今回困難なら、「Stop waiting」に名称変更し、サーバ処理完了までは全モードのGenerateを無効にする。真のCancelは別issue化する。

設計の骨格は良いものの、現状は公開契約と互換性に関わる未決事項が残っているため、実装開始前の差し戻しが妥当です。レビューは読み取りのみで、コード変更やテスト実行は行っていません。
